## 1. Assignment

## 4. Shared implementation rules

- Use a modular application with a separate worker process. Do not introduce unnecessary microservices.
- Keep business rules in shared services so web requests, workers and workflows use the same invariants.
- Validate all external input on the server. Client validation improves experience but does not provide security.
- Keep company ownership and permissions explicit on every operation.
- Use transactions and database constraints for correctness under concurrency.
- Keep long-running work out of HTTP request lifetimes.
- Use durable idempotency receipts and an outbox; queue IDs alone are not sufficient.
- Preserve immutable published test versions and final submissions.
- Never expose answer keys, hidden tests, private interview notes or unrestricted database entities to candidates.
- Do not run candidate code or SQL on the application host or application database.
- Never treat failed infrastructure, pending manual review or absent results as zero performance.
- Do not create fake success states to conceal missing providers.
- Use current compatible stable dependencies, lock versions and document important deviations from the original stack.
- Local email capture is the default. Do not send to real recipients, purchase infrastructure or publish externally without authorization.
- If the current hosted environment cannot run workers, provide separately deployable worker infrastructure and a working local stack. Do not disguise a browser timer or request handler as a durable queue.

## 10. W06 — Reliable test delivery: 4,000 planned lines

Suggested modules: `assignment-service`, `attempt-service`, `response-service`, `submission-service`, `expiry-sweep`, candidate test components and recovery state.

### Invitations and start

- Assign tests individually and in validated bulk operations.
- Distinguish start-by from hard-finish-by.
- Opening an email link or instructions page does not consume an invitation or start time.
- Explicit start verifies ownership and atomically creates at most one active attempt.
- Calculate deadline from base duration, accommodation multiplier and extra seconds, capped by hard finish.
- Obtain authoritative time after lock acquisition; do not rely on a stale transaction-start timestamp after waiting.

### Autosave

- Save typed answers with expected revision and unique client mutation identity.
- Same mutation/same payload returns the original acknowledgement; changed payload conflicts.
- A stale revision cannot overwrite a newer answer.
- Show unsaved, saving, saved, offline and conflict states honestly.
- Preserve acknowledged answers across refresh and reconnect.
- A replay of an already accepted save may return its original acknowledgement after expiry; a new late save must fail.
- Test on two browser tabs, reconnects and intentionally out-of-order responses.

### Deadlines and submission

- Check state and authoritative time on every new answer mutation.
- Reject answers arriving exactly at or after deadline.
- Lock the attempt consistently when saving or finalizing.
- Finalize one immutable snapshot and receipt; repeated submits return that receipt.
- Ensure a manual-submit/expiry race produces one final snapshot and one grading event.
- Worker downtime never extends permitted answer time.
- An expiry sweep repairs missed jobs using last acknowledged responses.
- Retakes create new attempts; they never overwrite submitted evidence.

### Candidate experience

Implement question navigation, answered count, review-before-submit, clear deadline/timezone, accessibility accommodations, file/recording alternatives, receipt, and policy-controlled feedback. No hidden demographic inference or automatic cheating verdict based on tab switching.

Exit gate: concurrency and boundary tests prove no lost acknowledged answer, duplicate final submission or accepted late answer. Browser tests demonstrate recovery without claiming unsaved text was persisted.

## 21. Concrete critical contracts

Implement these contracts in the current architecture or document equally explicit equivalents.

### Idempotency

Uniqueness: `(actor, company-if-applicable, operation, idempotencyKey)`. Store a canonical payload fingerprint as a compared value, not inside that uniqueness key. Same key plus same payload returns original outcome. Same key plus changed payload returns conflict. Handle concurrent requests transactionally.

### Attempt timing

`effectiveSeconds = ceil(baseSeconds * multiplierBasisPoints / 10000) + extraSeconds`.

`deadline = min(startTime + effectiveSeconds, hardFinishBy when present)`.

New responses require `state == IN_PROGRESS` and `authoritativeNow < deadline`. Read authoritative time after acquiring the relevant lock. An explicit extension is audited and changes the current deadline, not past accepted response timestamps.

### Submission

Acquire attempt lock; authorize; return existing receipt if finalized; verify state/time/expected revisions; snapshot acknowledged answers; write final state, receipt, audit and outbox in one transaction. Never await an external grader inside this transaction.

### External effects

Persist intent, use provider-supported idempotency when available, call outside the database transaction, persist known result. Timeout/crash after possible acceptance means reconcile or `UNKNOWN`, not guaranteed failure. Domain exactly-once outcomes and third-party exactly-once delivery are different guarantees.

### Scoring

Keep exact raw points and weights. Missing grades remain pending. Only finalize when required sections are evaluated. Threshold decisions use exact values. External scales retain provenance and are not blindly normalized against unrelated assessments.

### Safe output

Build allowlisted candidate/public DTOs from permitted fields. Do not serialize unrestricted ORM records and hope that removing a few keys is sufficient. Include tests with secret sentinel strings in hidden cases and internal notes; prove absence from candidate JSON, HTML, cached responses and relevant bundles.
